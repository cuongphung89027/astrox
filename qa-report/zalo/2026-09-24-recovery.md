# Zalo sign-in incident — 24 September 2026

## Confirmed evidence
- Production login_diagnostics: server_verify_failed at 03:06:27 and 03:06:40 UTC, provider HTTP 200 with JSON error -501. Token exchange reached the profile verification step.
- The issue predates the login-popup redesign; prior diagnostics on September 22–23 contain the same provider error.
- The prior browser-supplied identity fallback was retired in 4fc90af because identity could be forged. It remains disabled.
- Local unauthenticated graph endpoint responds with error 100 (missing access_token); this does not prove an authenticated request or production connectivity works.

## Shipped mitigation
Browser callback failures now render a short AstroX recovery page with retry/home links, a restrictive CSP and no-referrer. API callers retain JSON/status contracts. The page clears the temporary OAuth cookie and never creates a session or includes callback codes/tokens. Retry starts a fresh OAuth flow.

## Validation
- Two new regression cases failed against old raw-JSON behavior, then passed.
- 156 backend/admin/reward tests pass, including existing verified-server-login and rejected client-identity tests.
- Worker dry run succeeds. Local browser displays the recovery page and links.

## Unresolved
This is a UX mitigation, not a resolution of provider error -501. No authenticated successful Zalo sign-in was demonstrated. Network/IP restrictions remain a hypothesis requiring a trusted server path and real authentication verification. Asked operator whether an existing Vietnam-hosted server is available; no credential requested. Do not restore client-trusted identity or route access tokens through public proxies.
